## 什麼是 API？

在解釋 RESTful API 前，我們先簡短解釋一下什麼是 API～

API 是程式與程式之間的溝通橋樑，依規模大小可以是系統與系統之間的溝通，小到可以是函式與函式間的溝通，API 全名是應用程序接口（Application Programming Interface），其中接口代表是可以溝通的入口，必須要符合接口的規範，才可以達成有效的溝通。

在 Web 應用程式中，我們常說的 API 是 Web API，它對外提供了一些接口讓大家使用，當然需要符合接口的規範（query string、驗證……）才可以對 server 達成有效的訪問，並進行業務上的操作。

## 那什麼是 REST？

REST 全名是表徵性狀態轉移（Representational State Transfer）。

REST 是一種面向資源的架構風格，以單一資源或資源集合來命名，由於 REST 以資源為中心，不能使用帶有動詞的方式來命名。

如果不能使用帶有動詞的方式命名，我們要怎麼做 CRUD 呢？可以透過 HTTP 動詞對資源進行操作：GET、POST 兩個的 URL 一樣，PUT、PATCH、DELETE 三個的 URL 一樣，卻因搭配的 HTTP 動詞不同，而產生了對資源的不同操作。

乍看之下，其實兩個 URL 都是合法的，但以 REST 風格來說，Query String 只應包含過濾條件或參數，不應該包含資源識別（鍵值）。

## REST 的 6 個約束

要達成 REST 架構風格，需符合 REST 的 6 個約束，才能稱為 RESTful 服務（REST 與 RESTful 的差異在於一個為名詞一個為動詞）。6 個約束如下：

1. **客戶端－伺服端（Client-Server）**
   前後端分離，客戶端與伺服端各自獨立開發，不需要管背後使用了哪些技術、語言，只要符合 API 接口的規範，即可達成數據溝通，體現了關注點分離原則。
2. **無狀態（Stateless）**
   每一次請求都是獨立的，伺服端不能儲存和紀錄客戶端的狀態資訊，須由客戶端自行儲存。客戶端會將所儲存的狀態資訊透過 URL 參數或 header 來發送請求，伺服端再根據狀態資訊來處理請求。
3. **快取（Cache）**
   伺服端在 response 時，需指名快取的特性，讓客戶端或網路中介可以將 response 快取起來，有效的管理快取機制，有利於減少客戶端與伺服端之間的溝通。
4. **統一介面（Uniform Interface）**
   統一介面是 RESTful 設計的基礎，包含了 4 個子約束：
   - **資源識別**：面向資源，透過唯一的 URI 來區別資源。
   - **以表示操作資源**：客戶端在請求資源時，可以指定回傳格式（JSON、XML、……）。
   - **自我描述訊息**：伺服端和客戶端在每一次溝通，都有足夠的訊息來自我描述資源的相關訊息，比如回傳格式、cache 狀態、資源相關操作連結等等。
   - **超媒體應用狀態引擎（HATEOAS）**：伺服端在回覆響應時，除了包含請求資源本身外，也須包含對資源操作的相關連結，比如在獲取（GET）資源時，同時包含了更新、刪除該資訊的相關連結。
5. **分層系統（Layered System）**
   在客戶端與伺服端之間佈署中間服務（proxy、api gateway……），而客戶端和伺服端不知道中間服務的存在。中間服務主要用於加強負載平衡、資安、緩存等目的。
6. **按需代碼（Code-On-Demand，可選）**
   伺服端通過傳遞可執行代碼給客戶端，為客戶端提供客製化、擴充性功能，但此約束增加了客戶與伺服端之間的耦合，故該約束為可選。

## 一定要符合 RESTful 架構風格嗎？

不一定，像黑大就對 RESTful 有不同見解。

依自己或開發團隊開發習慣，來決定是否要使用 REST。小愛個人的習慣是盡量遵循 REST 的開發規範，但若遇到規範上的限制，導致開發上變困難麻煩，還是可彈性調整的，舉例來說，REST 是面向資源（e.g. `/users/1234/`），若面向過程（e.g. `/login/`），是無法使用資源來命名的。

## 統整

以下簡易地統整如何設計 RESTful API 的小技巧：

- 正確的使用 HTTP 動詞、HTTP header、HTTP Status Code
  - 使用 HTTP 動詞來針對資源進行 CRUD 操作
  - e.g. 指定資源的回傳格式，應使用 header 的 `Accept`。
  - e.g. 創建資源成功時，應回傳 201（Created）狀態碼；禁止訪問資源，應回傳 403（forbidden）。
- 使用名詞複數表示資源集合，e.g. `alice.learn/products`
- 以 `/` 斜線表示資源之間的層次關係，e.g. `alice.learn/products/1234/images`
- 若一個操作無法對應到資源的某個操作時，可適當的在 URI 包含動詞，但需要基於一個資源的 URI：

```text
// 以下的 set-admin 是基於一個資源的 URI
PUT /users/1234/set-admin    // 更新使用者 1234 的管理員設定
DELETE /users/1234/set-admin // 刪除使用者 1234 的管理員角色
```

- 使用 Query String 來針對資源進行過濾、查詢、分頁等操作（注意：不應包含資源的識別值）：

```text
// 針對資源進行過濾、查詢、分頁等操作
GET /products?category=game
GET /products?search=alice
GET /products?pageSize=10&pageNumber=3

// 不應包含資源的識別值
GET /products?id=1234
```
